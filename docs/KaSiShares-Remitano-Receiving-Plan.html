KaSiHub / KaSiShares
Implementation brief
11 August 2026

Remitano as the receiving point for KaSiShares purchases.

A controlled path for international USDT income: two locked receiving routes, verified payment evidence, and no automatic share issuance.

THE OBJECTIVE

Accept USDT safely without turning an exchange deposit into a share ledger.

Buyers may pay an approved obligation via Remitano. KaSiHub independently verifies the transaction and only then permits the controlled allocation workflow.

2separate network routes: TRON and BNB Smart Chain
THE KEY DISTINCTION

Money received ≠ shares issued.

Receiving USDT proves neither identity, eligibility, allocation availability, nor legal acceptance. Those gates remain inside KaSiHub.

This avoids a dangerous shortcut where a provider callback or wallet deposit automatically changes ownership records.

01 / Controlled payment flow
KaSiShares × Remitano

The safe flow

The buyer never chooses an arbitrary wallet. KaSiHub binds the obligation to one approved network, token, receiver, amount, and expiry.

KYC-approved buyer
KaSiShares reservation
Locked USDT obligation
Remitano route / payment request
TRON or BSC transaction evidence
KaSiHub reconciliation
Controlled allocation queue
Issuance only after approval

What Remitano does

  • Provides the controlled collection endpoint or payment-gateway charge.
  • Returns provider events / payment status where supported.
  • Receives the USDT into the approved route.

What KaSiHub must still prove

  • Buyer identity and eligibility.
  • Correct USDT contract, network, receiver, amount, and confirmations.
  • One-time reconciliation and an authorised allocation decision.

03 / Execution sequence
Smallest safe path to live collection

Four release stages

STAGE 1

Provider onboarding

Confirm account permissions, choose charge vs. receiver model, reissue credentials, and store replacements in Encore secrets.

Exit: no secrets exposed; provider contract known.

STAGE 2

Route configuration

Register the exact TRON and BSC receivers with their approved contracts and confirmation thresholds.

Exit: two routes are independently testable.

STAGE 3

Adapter and reconciliation

Add server-only provider client, signed callback verification, idempotency, transaction matching, and operator review states.

Exit: test suite proves every rejection path.

STAGE 4

Staging pilot → production

Run one small controlled payment per network, validate financial records, then release through a rollback-safe deployment.

Exit: public collection is enabled only after evidence.
